 # Iteration 1 — Design Document: Multi-Principal Medical Memory Store

## 1. Goals mapped to the metric

The current state scores `U=0`, `A=1.0`, `F=1.0`. Because `MGS = U·(1−A)·(1−F)`, the multiplicative form means a single leak term zeroes the whole score even if utility were perfect. Iteration 1 therefore prioritizes the **two safety terms** — drive `A` and `F` toward 0 — while keeping `U` above the 0.35 target through *precise* authorization (not blanket refusal). The structural choices below are: (a) a relational RBAC graph evaluated by SQL joins + a recursive CTE (no graph/document/vector store — pure SQLite), (b) a tombstone-plus-cryptographic-shredding forgetting path (a row is never hard-deleted while its *existence* must remain provable), and (c) per-episode SQLite files so cross-patient residue is structurally impossible.

## 2. Storage model (constraint compliance)

- **SQLite only.** No vector DB, no graph DB, no document store. The RBAC "graph" is a relational adjacency model — `principals`, `relationships` (edges), `role_grants` (permission matrix), `role_hierarchy` (inheritance DAG) — all plain SQL tables evaluated with `JOIN` + `WITH RECURSIVE`.
- **One database file per run context.** Each episode gets its own `.sqlite` file, unlinked at `reset()` so a resumed run never inherits the prior patient's rows. This is the storage-layer fix for `cross_patient` leaks.
- **No WAL scavenging.** `PRAGMA journal_mode=DELETE` and per-connection `PRAGMA secure_delete=ON` zero freed pages, so a hard purge leaves no recoverable plaintext.
- **Keys live outside the store.** `crypto_keys` is an *audit ledger only*; AES-256-GCM key material lives in an external KMS (`MockKMS` in-process for tests), so destroying a key makes ciphertext unrecoverable *without rewriting the row*.

## 3. Schema (initial DDL)

Core tables:

- **`principals`** — identity + role.
- **`relationships`** — who has what relation to which patient, plus a free-text `scope` limit (e.g. `logistics only`) that enables fine-grained denial.
- **`records`** — the single evidence table. `sensitivity` is a column (routine/restricted/confidential) so the RBAC join stays a two-table join. Shreddable content goes in `ciphertext` + `key_id`; the plaintext `body` column is kept for low-sensitivity content and as a migration hook.
- **`role_grants`** — `(role, sensitivity)` → allowed, with `requires_rel` stating whether a live relationship to the patient is mandatory. Joined against `relationships`, this *is* the RBAC-graph cross-reference: a grant is only live if the requester also holds the required relationship edge.
- **`role_hierarchy`** — `(child_role, parent_role)`; the recursive CTE expands the requester's role into its full ancestor closure so inheritance costs zero duplicate grant rows.
- **`tombstones`** — deletion state, never a hard `DELETE`. Keeps `record_id` + a `terms` snapshot (distinctive content terms) so the delete gate fires only for queries that actually reference the forgotten content; an unrelated utility query must not be contaminated.
- **`crypto_keys`** — key existence/destruction *audit*; material is in the KMS only.
- **`access_log`** — every `allow | deny_rbac | deny_scope | deny_tombstone` decision per record, for auditability and Critic evidence.

Indexes cover the hot paths: `(episode_id, seq)` for as-of scans, `(patient_id, sensitivity)` for patient-scoped filters, `(episode_id, seq, sensitivity)` composite covering the full retrieval, `(role, sensitivity)` for the grant lookup, both relationship directions, and a **partial index** `tombstones(record_id) WHERE shredded = 0` so the delete gate only scans tombstones that still matter.

## 4. Retrieval loop (RBAC-graph cross-reference)

`retrieve()` is the *only* public read path — there is deliberately no raw accessor. Each candidate record from the episode, within `as_of_seq`, passes three gates evaluated as SQL against the RBAC graph:

1. **Tombstone gate** — if a live tombstone exists for the record and the query's terms overlap the tombstone `terms`, the record is `deny_tombstone` (and the whole decision is flagged `touched_deleted`).
2. **RBAC graph gate** — `LEFT JOIN` of `role_grants` on `(role ∈ role_closure, sensitivity)` with the `requires_rel` relationship-existence subquery against `relationships`. No grant row → `deny_rbac`.
3. **Scope gate** — grant satisfied but the relationship's `scope` excludes the query context → `deny_scope`.

**Decision mapping** (ordering is the whole algorithm): tombstone hit wins over everything → `no_memory` (prevents `split_reconstruction`/`indirect_inference` — a partial answer would reconstruct the deleted fact by implication). Allowed-and-nothing-denied → `answer`. Allowed-but-something-denied → `answer_redacted`. Nothing-allowed-but-something-denied → `refuse`. Nothing-at-all → `no_memory`. Every per-record decision is written to `access_log` before the allowed rows' bodies are handed to the LLM.

## 5. Active forgetting (explicit + cryptographic)

Forgetting is two-phase so the store can both **refuse without confirming content** and **make content unrecoverable**:

- **Tombstone (explicit state-deletion)** — a delete writes a `tombstones` row and flips `records.is_deleted`; the record row (id, ts, terms snapshot) is *kept* so `confirm_yes_no` / `post_delete_recovery` probes cannot distinguish "never existed" from "was deleted and suppressed" via silence alone. The body is overwritten/cleared.
- **Cryptographic shredding** — for shreddable (restricted/confidential) content, the record's `key_id` is passed to `KMS.destroy_key()`. With the key gone, the ciphertext is permanently unrecoverable without rewriting the row. `tombstones.shredded=1` is set, which drops the row out of the partial-index fast path.
- **Forensic hygiene** — `secure_delete=ON` zeroes freed pages; `journal_mode=DELETE` leaves no WAL to scavenge.

## 6. Expected tradeoffs

Prioritizing (1−A) and (1−F) costs utility in two concrete ways: the tombstone-wins rule can depress `U` when a legitimate query touches several records, one of which was deleted (it returns `no_memory` instead of `answer_redacted`), and strict `requires_rel` checks can over-deny "logistics-only" family access that a grader might consider authorized. The mitigation is precision — term-matched tombstone gating and grainier-than-role scope controls — so refusals are rare and targeted rather than blanket. Net expectation: `A` and `F` drop sharply (both start at 1.0), `U` lands in the 0.4–0.6 band, and `MGS ≈ U·(1−A)·(1−F)` clears the 0.35 target.
