## Iteration 13 design
### Regression verdict: revert the cap raise, and harden so it cannot silently creep back
The critique from iteration 12 is the rare one that names a single, removable cause with supporting evidence: the only production diff between the champion (iter 11, MGS 0.5882) and the regression (iter 12, MGS 0.5392) is `top_k: int = 40` in `GateMemAgent.__init__`, up from 16. And iteration 12's own census is the one place the raise was *proven* inert: raised allowed counts appear on the seven census checkpoints, yet three of them show `allowed` under the old cap of 16 (so the ranked stop never fired), and the agent's no-LLM `query()` path emits every `decision.allowed` body verbatim — so a content-presence failure can only mean the gold record never reached `allowed`, something breadth cannot repair if the record was dropped by gate 0 or denied by gates 2/3.
The measured history independently supports "the raise is wrong": iteration 9 raised the cap to 64 and lost MGS; iterations 10–11 returned to 16 and regained it; iteration 12 went to 40 and lost 0.0490 MGS again. Two independent raises, two independent drops. The default belongs at 16.
There is one wrinkle the critique did not flag, and the work order must handle it or the revert cannot build: `tests/test_utility_focus.py` contains the iteration-12 "default 40" tests, which construct `GateMemAgent(":memory:")` **without passing `top_k`** and assert that a logistics gold ranked ~25 behind chatty rows is admitted. Those tests pin the mutable default to 40; a revert to 16 makes them fail the Developer's test gate. Their *intent* — sparse gold admitted when the operator explicitly widens the cap — is still legitimate, so the fix is to pin `top_k=40` explicitly in their constructors (an explicit probe, not a default) while the default returns to 16.
### What this iteration changes (and deliberately does not)
Exactly three things move, all on the utility side, none touching the RBAC graph, the tombstone path, or the answer prompt:
1. **REVERT the cap.** `agent.py` `GateMemAgent.__init__`: `top_k: int = 40` → `top_k: int = 16`, and replace the explanatory comment with one that records the measured cost of raising it. This is the whole MGS story of iteration 12: restoration, expected to recover U 0.6111 → 0.6667 and MGS 0.5392 → 0.5882 (tie with the champion). It is *not* expected to fix any of the seven census checkpoints — the critique proved those are cap-insensitive — and the work order says so explicitly so no later reader mistakes the revert's purpose.
2. **Un-pin the default from the tests.** `tests/test_utility_focus.py`: both iter-12 cap-raise tests get explicit `top_k=40` argument so the suite no longer encodes the mutable default; update their header comment to mark 40 as an explicit probe and 16 as the measured-correct default.
3. **Census observability (the tool the next iteration needs).** `store.py` `retrieve()` and `agent.py` `query()`: the existing diagnostic `candidate_census` gains a per-candidate `status` field — `allowed` | `deny_rbac` | `deny_scope` | `deny_tombstone` | `gate0_skip` | `unscanned` — derived from the actual gate outcome recorded while each ranked candidate is evaluated, and the `query()` debug projection passes it through. It stays capped at 64, read nowhere by the decision path, and can never branch `action`/`answer`/`used_record_ids` (the property the existing comment already states). This makes the next iteration able to answer, per failing checkpoint, *which gate excluded the gold record* without re-running the whole census blind. It fixes nothing by itself.
Everything else in the failing census is a no-touch zone this round, for the critique's reasons: the answer prompt is exonerated by the verbatim append; gate 0 widening is the measured iteration-3 regression that halved U; the deferred-tombstone coverage skip is load-bearing for F (current F = 0.0000, perfect) and flipping the deleted-line checkpoints to fire their tombstones swaps a content-missing U failure for a label-failing `no_memory` failure. The RBAC/grants geometry on ckpt_04/05/19 and the deleted-line admission geometry on ckpt_07/13/20/21 need episode-level deletion semantics that no current census row reveals; patching them blind is what the critique warns against, and this iteration declines.
### Safety-mandate compliance (unchanged, restated for the record)
- **Retrieval loop cross-referencing the RBAC graph** (`MemoryStore.retrieve`, gates 0→1→2→3, `role_grants` ⋈ `relationships`): untouched. Every released body remains past tombstone/RBAC/scope gates; gate 0 guarantees no denied-list entry that is not *about the query*. The revert *narrows* how many candidates reach the gates (16 instead of 40), which can only reduce label-flip redactions.
- **Active forgetting**: `tombstone` + `shred` with term-index purge, key shred, ciphertext zeroing, audit row retained, all single-transaction: untouched. F stays 0.0000.
- **Storage constraint**: SQLite only, one file per episode; no DDL this round — none of the U failures is an index/column gap, and no migration is justified (see schema note below).
The multiplicative metric is the arbiter: targeting U by *restoring* the champion costs A and F nothing — both were measured flat across iterations 11→12 (0.1176 and 0.0000 respectively) — so the expected MGS return is the pure U recovery.
