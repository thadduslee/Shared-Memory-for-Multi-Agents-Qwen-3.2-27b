# Iteration 15 — Design
## What the loop has actually measured
The relevant evidence, read cold:
| iter | change | U | A | delta | verdict |
|---|---|---|---|---|---|
| 11 | cap 16 + allowed-list ranking | 0.6667 | 0.1176 | +0.0131 | champion (still) |
| 12 | **cap 40** | 0.6111 | 0.1176 | −0.0490 | regression |
| 13 | **cap back to 16**, census `status` added | 0.6667 | 0.1176 | 0.0000 | tied (census inert, not adopted) |
| 14 | census work order | — | — | — | never built: grep-tool error, then `finish` twice rejected "no source changed" |
Three consecutive iterations moved the **cap/rank of the pre-gate scan** (11's champion cap, 12's raise, 13's revert) and the effect was a tie or a loss. The census field the critique of iter 13 calls "inert by construction" is **already present and passing tests in this workspace** — the iter-13 critique's P0 ("re-add status to the champion") is satisfied here; tests `test_census_status_is_diagnostic_and_from_allowed_set` passes at local gate 1.000. So iteration 15 must **not** re-add diagnostics, and must **not** move the cap again. The only behavioural lever left with any measured signature is the **content-presence gap itself**, and the signature that survives every cap value is:
> the judged logistics string is missing from the final answer **even though the answer path re-emits every `decision.allowed` body verbatim**, and no rescue scan has ever been run against the full as-of shard.
Every prior fix (cap 8/16/40/64) was applied **before** the deny gates, on the ranked top-k candidate scan. The gold record, however it was dropped — gate-0 lexical miss (paraphrase), or overlap-rank crowding below the allowed cap by restatement chatter inside these long `deleted_*_line` episodes — is *never seen by any of them*. None of those designs ever asked the opposite question: *after* the answer is assembled, is there a **fully gate-cleared, non-tombstoned** record in the shard that literally carries a required logistics token the answer is still missing?
That question is a genuinely new mechanism (iterations 11–14 all resized or instrumented the scan head; none re-scanned at **answer time**). It targets U only, and can only **add** evidence that already passed the identical tombstone/RBAC/scope gates — so A and F are structurally untouched. That is the design.
## The change
Add a second-chance **required-logistics rescue** to the deterministic (`self.llm is None`) answer path in `GateMemAgent.query`. After the allowed-body join and the existing `_logistics_suffix` pass, call a new `MemoryStore.rescue_missing_logistics(...)` that:
1. scans all **live (non-tombstoned), ≤ as_of_seq** records for this patient,
2. keeps only records whose body contains a logistics-class token (dates, times, mg/dose, weekday/month, contact/phone) **absent** from the current answer,
3. runs each through the **same per-record tombstone → role×sensitivity grant → relationship → scope checks** that `retrieve()` already applies to build `allowed` (same helper code path — no new policy),
4. returns ≤`LOGISTICS_RESCUE_LIMIT` (default 8) `Evidence` objects that cleared every gate,
5. and the agent appends their bodies under the existing verbatim `"Details: "` lead, keyed by record_id so an already-allowed record is never duplicated.
Because release is gated by the *exact* logic already used to clear `allowed`, a rescued record is strictly a record that a full scan **would** have allowed — the rescue only repairs the lexically-blind top-k/rank admission, never the policy frontier. A tombstoned or scoped-out record still fails the same checks, so F and A cannot move; only the utility of an authorized, miss-scanned gold is restored.
The patterns are shared: move `_LOGISTICS_PATTERNS` out of `agent.py` into `store.py` (as `LOGISTICS_PATTERNS`) so the rescue token check and the agent suffix pass use the identical matcher (no cycle: `agent` imports from `store` already).
**Why this is not a fourth re-measurement of the cap:** the rescued records are found by a **content pattern over the whole shard**, independent of overlap ranking or the top_k stop. If the gold dropped at gate-0 (paraphrase miss — e.g. "portal fine" vs "portal okay"), the pattern scan finds it directly. If it dropped to rank 17+ under the allowed cap (restatement flood), the rescue restores it verbatim *after* the cap has done its contractual job, leaving the capped decision intact. Both failure modes the critique left open are addressed by one mechanism that honours every hard-cap test.
**Why A and F are safe** (the multiplicative risk): the rescue path is reached only inside `action in {"answer","answer_redacted"}` and the existing `no_memory`/`refuse` branches return before it, so a responsive tombstone still short-circuits to `no_memory` (F preserved, and `test_a_tombstone_beats_everything`/`test_tombstone_beats_authorization` still hold). The released set is a subset of what an overlap-blind full gate pass would release for that same requester — the A-side fixtures (`test_cap_raise_does_not_leak_confidential_or_restricted_bodies`, `test_family_gets_no_confidential_even_on_routine_query`, `test_family_scoped_to_routine_only`) can only be satisfied because rescue reuses the same grant/scope decision rather than widening it.
**Ckpt_04 caveat:** `..._010_..._ckpt_04` is a *label flip* (answer→answer_redacted, `denied_rbac=3`): responsive content is genuinely withheld from a requester the judge expects to see it. Rescue cannot fix a label flip (it never widens denials), and per the iter-13 critique that sub-mechanism must **not** be folded into the content-missing story. This design deliberately does not touch grants geometry this round — that is the census-named fix the next iteration should make if the run dumps `deny_rbac` on gold records 04/05/16; here we fix the three-plus content-missing whose `denied_rbac=0` proves no policy hole (09/10/03 and, if its denials are incidental, parts of 05/16).
## Build-failure mitigations (iter-14)
- Step 7 failed because the work order called the non-existent tool `grep`. This work order performs the whole shard scan **in Python inside `retrieve`/a new store method** — no tool outside the allowed set (`read_file`, `apply_patch`, `run_tests`, `compile_check`, `run_sandbox_smoke_test`, `sql_exec`) is referenced.
- `finish` was rejected twice because no `.py`/`.sql` file had changed; the work order is now a **delta that necessarily edits `memory_system/store.py` and `memory_system/agent.py`** (new method, new pattern constant, new call site), so a green finish cannot fire on an unchanged workspace. Steps are ordered to patch first and call the gates once at the end; `finish` appears exactly once.
## Expected effect
`targets_metric`: **U** (raise utility_accuracy on the 5 content-missing `answer` checkpoints). `expected_tradeoff`: A ≈ unchanged (only records passing the identical RBAC/scope/tombstone gates are ever added to the answer; nothing is ever removed from a denied list), F ≈ unchanged (tombstone short-circuit precedes the rescue path). If the mechanism restores e.g. 4–5 of the six, U moves 0.6667→~0.8889 and MGS ≈ 0.889×(1−0.1176) ≈ 0.78 — a clean new best without touching A or F.
