# Iteration 17 — Design
## Reading the table
Five measurements separate the two U eras of this run: at U=0.6667 MGS is pinned at 0.5882 by six `answered_but_content_missing` checkpoints (010/011/013/019/020/021), and iterations 13, 15, and 16 each tied it with different code. The critique of 16 is the first one that actually isolates *why* the plateau is invariant: for 013/019/020 (`allowed == 16`, the cap) the same-gates rescue — which ignores `top_k` — returned nothing; and for the deny-free ones (013/020/021, `denied_rbac = 0`) the answer already appends **every** `allowed` body verbatim, so gold absent from the answer means gold absent from *every allowed record*. That is a sharp, largely correct deduction: it says the gold is not in any responsive-and-cleared live record.
But the deduction rests on one premise the critique itself flags as never audited: that `rescue_missing_logistics` actually scans **all** of the patient's live, cleared records. Its docstring claims that, and the critique's verdict ("top_k-ignoring same-gate recovery = 0") is only evidence about the gold's *absence* if the rescue's candidate set really is unbounded. The method was in the truncated half of `store.py`; nobody read it. Four iterations of moving the *call site* of the rescue (no-LLM branch → LLM branch → both) all tied, and that is exactly what you would see if the rescue itself were bounded internally the same way `retrieve()` is — e.g. building candidates from a shared-term-hash join with the query, or a `top_k`, or a gate-0 overlap floor — because then it could never reach a gold record whose body shares **zero** indexed terms with a paraphrase query. A logistics question says "what time is the ride," the gold record says "transport pickup Tuesday at 9:15 from the lobby," and if neither side shares a content digest the two never meet in any overlap-bounded scan — while the record sits there, fully cleared, perfectly readable, right next to the denial-free census. That hypothesis is consistent with every measured number, including the deny-free checkpoints, and it has never been tested because the rescue's internals were never inspected.
So iteration 17 does **one narrow retriever-side thing** the critique did not falsify (it only could not observe it), and pairs it with the provenance diagnostic the critique demanded, so whichever way the run lands we finally learn where the gold lives.
## The change
**Work item 1 — `memory_system/store.py::rescue_missing_logistics`: make the candidate supply un-bounded by query overlap.** Instruct the Developer to audit the method and ensure its candidate set is built in SQL as: the patient's **live** (non-tombstoned) records with `seq <= as_of`, filtered by the *same* role × sensitivity × scope grant join `retrieve()` applies (records/relationships/role_grants), and **not** bounded by a shared `term_hash` with the query, not by a `top_k`, and not by a gate-0 overlap floor. If any such bound exists, remove it. Then emit each body that carries a `LOGISTICS_PATTERNS` token absent (case-insensitive) from the current answer. Any ordering/cap that is kept (`limit=8`) must be applied **after** the token filter, never before, so a sparse gold cannot be starved out by `limit=8` chatty earlier rows. Keep the signature identical. This is SQL; no DDL needed, and it stays within the SQL/SQLite-only constraint.
**Work item 2 — one regression test** (add to `tests/test_utility_focus.py`) that the existing iter-16 test does not cover: a cleared routine logistics gold whose body shares **zero** indexed terms with the query (pure paraphrase divergence), assert `rescue_missing_logistics` returns it while the iter-16 behavior (gold overlapping 3 terms, below top_k, on the LLM path) still passes. The new test proves the un-bounding; it fails against the current (un-audited) code if that code is overlap-bounded, which is how the Developer knows the fix landed.
**Work item 3 — provenance diagnostic, inert on every decision path.** Widen the existing `Decision.candidate_census` population in `store.py` so it also records, for each patient record (live *and* tombstoned) reachable `as_of` that carries any `LOGISTICS_PATTERNS` token: disposition drawn strictly from the fixed status set the iter-15 test enforces (`allowed`/`deny_rbac`/`deny_scope`/`deny_tombstone`/`gate0_skip`/`unscanned`), plus `has_logistics` and `token_in_answer` flags. Extend the agent debug-projection key tuple in `agent.py` to pass the new keys through. This never branches action/answer/`used_record_ids`; it just makes the next critique decisive about which of the six are policy-denied vs. data-capped vs. paraphrase-mismatched.
## What does not change
`top_k = 16` stays (iter-12's raise is a measured regression). `role_grants` stays (adding `billing` is a measured A regression). Tombstones and `sanitize_and_decide` ordering stay. The action-labelling path is untouched. The change is confined to (a) which *cleared, live* bodies the rescue may reach, and (b) inert observability.
## Terms
**Targets:** U — the six `answered_but_content_missing` checkpoints, via closing the paraphrase-overlap gap so a cleared routine logistics record whose body carries the answer's token but shares no indexed term with the query can finally reach the `Details:` append.
**Cost to A:** structurally ~zero. The rescue emits only records already cleared by the identical RBAC × scope matrix `retrieve()` applies, and only on an `answer`/`answer_redacted` action; a protected body is denied at the same grant filter and never surfaces. There is a small theoretical cost — appending a *cleared-but-not-query-responsive* routine body widens the surface a human might judge as beyond the ask — which is why the fix is kept to logistics tokens and is trivially revertible if MGS dips.
**Cost to F:** zero by construction — tombstoned records are excluded from the rescue's candidate set, and the census is read-only.
**Numeric band:** fixing just 1 of the 6 gives U=0.7222 at A=0.1176, MGS ≈ 0.637 (new best, +0.049). A full 3–6 fixed pushes MGS to 0.65–0.67. If instead the run ties — the census will then show the gold as `deny_*`/absent for all six — that is still the information P1 of the critique demanded, and the next iteration stops spending shots on retrieval.
**Revert instruction if it regresses or ties again regardless of the census:** delete the `_rescue_append` block inside the `self.llm is not None` branch of `GateMemAgent.query` in `agent.py` (iter-16's edit) and, if the tie persists with the census silent, drop `rescue_missing_logistics` from the codebase entirely, restoring the iter-11 body-join-only answer assembly that first produced 0.5882.
