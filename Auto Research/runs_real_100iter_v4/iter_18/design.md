## Iteration 18 design — stop widening, start seeing where the gold lives
**What the table says.** Five consecutive ties at MGS=0.5882, all on the same six checkpoints (010/011/013/019/020/021), all mechanism `answered_but_content_missing`. Iteration 17's one functional edit — un-bounding the rescue scan's candidate supply — moved nothing (+0.0000 on U/A/F), and the critique's own arithmetic proved it had nothing to reach: at `ckpt_021` every live, cleared, `seq <= as_of` record was already inside `decision.allowed` (allowed=13 < top_k=16) and every allowed body was appended verbatim on both answer paths, yet the gold date still wasn't there. Candidate-widening is measured dead. Pushing it a sixth time is the loop's most reliable way to burn an iteration.
**What this design does instead.** It takes the critique's P1 verbatim: an **observability-only** iteration. No retrieval gate, no rescue, no top_k, no grant row, no tombstone semantics changes — nothing that can move A or F or even re-order `allowed`. The single production change extends the diagnostic payload so the next round can read `predictions.jsonl` and classify each of the six fails into one of four disjoint explanations: (a) gold sits in a `deny_rbac`/`deny_scope` row → U is policy-capped, stop retrieving; (b) gold record is `seq > as_of` (post-horizon) → U is harness-capped, stop; (c) gold sits in a live, cleared, `seq <= as_of` row but the record was `gate0_skip`-skipped or `top_k`-cut and carries logistics tokens the rescue's pattern set still missed → the one design-fixable residual, and the only case that warrants further retrieval work; (d) no record carries the gold tokens at all → benchmark-synthesized content, nothing retrievable can ever fix it.
That is the narrowest possible change — the critique literally asks to ship nothing else until this census lands — and it is the only remaining choice that can tell us whether iteration 20 should be a retrieval edit at all.
**Why SQL is the right instrument.** The census is a per-patient row walk that has to be sorted by `seq` and joined against `tombstones`, so one new composite index (`records(patient_id, seq)`) turns the diagnostic pass into a straight indexed scan with no sort. A single `CREATE INDEX`; no new table, no data rewrite. The existing `candidate_census` (top-24 ranked, gate outcome per candidate) stays exactly as-is — it is load-bearing for `test_census_status_is_diagnostic_and_from_allowed_set`. The full-patient census rides in a *new* inert diagnostic field on `Decision` so the existing census contract is untouched.
**The fixed-status constraint is the design's one trap, and this design walks around it.** `test_census_status_is_diagnostic_and_from_allowed_set` hard-codes its allowed status set to `{allowed, deny_rbac, deny_scope, deny_tombstone, gate0_skip, unscanned}`. Post-horizon rows therefore cannot carry a new `post_horizon` status or that test breaks. The fix: a post-horizon row is reported with `status: "unscanned"` (it genuinely is not scanned — it does not exist as of the question) plus a boolean `is_post_horizon: true`. Rows that cleared policy but were truncated by `top_k` keep `status: "allow"` but gain `would_be_allowed: true`, which is precisely how we detect "cleared gold existed but the cap hid it" (rescue should then have caught it — and on the six it didn't, which is the evidence we collect). Every row also carries `has_logistics` and the actual `logistics_tokens` matched, so a human reading the JSONL can see whether any record in the store holds the missing "Friday April 4 at 2:00 PM" tokens at all.
**Cost honesty.** This iteration expects to *tie*, not beat. It targets U only in the sense of buying the information that decides every later U attempt; it deliberately spends a turn to stop guessing which of four mutually exclusive horizon explanations is true when three of them are unfixable-by-design. A/F cannot move — no release path changes, no deletion path changes. If the census comes back (c) for any checkpoint, the next iteration has a scoped, non-speculative fix to build; if (a)/(b)/(d), the honest outcome is that 0.6667 * (1 - A) is the ceiling of this store under this benchmark and the loop should stop spending on retrieval.
