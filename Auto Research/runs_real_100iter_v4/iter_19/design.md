# Iteration 19 — Design Document
## Verdict on where to spend this iteration
The last six iterations all tied at MGS=0.5882. Every one of them — 15–18 — pulled a lever on **retrieval or answer assembly** (rescue wiring, top_k raise→revert, verbatim body append, rescue unbinding, an observability-only census). All are measured dead: the iteration-17 arithmetic in the critique proves that for the six content-missing checkpoints (010/011/013/019/020/021), every live, cleared, `seq <= as_of` record body is already inside `decision.allowed` and appended verbatim to the judged answer, so the gold token is **not in the retrieval surface**.
I am not pulling that lever a seventh time. The one mechanism that has **never** been touched, and that the critique identifies as the only place a U failure can be *created by the agent itself* rather than by the harness, is the **deletion path**: `store._honor_deletion_request`. Each of the six checkpoints lives in a `*_deleted_*_line` episode, i.e. an episode whose rewrite deleted a contact/scheduling line. Iteration 18's census is already present in this workspace (agent.py emits `patient_census`, `idx_records_patient_seq` is applied), so per-query visibility exists — but there is **no visibility into tombstone decisions**. The gold is either post-horizon (harness-capped, no store change fixes it) or inside a record the deletion matcher wrongly tombstoned because it shared ≥2 facility/contact terms with a `"delete the River House line"` request. `tombstone()` then sets `body = ''`, destroying the appointment's date/time that the later query legitimately needs.
The design below makes the deletion matcher **location-aware** so it can tell the line record the request truly names (phone-bearing, standing contact) apart from an appointment/scheduling record swept in purely by shared location + contact-sense vocabulary. It runs **before** `tombstone()` is called, so:
- it never resurrects a body (nothing to delete is un-deleted),
- it never weakens F — an F probe can only fire on a record the request genuinely covered, which this guard still deletes (phone-digest or real-content overlap overrides the sparing),
- it touches none of the RBAC gates and none of the release surface — A is bit-identical.
What it buys, at best: the 4–6 U checkpoints whose gold was swept into the graveyard by over-match. If instead those golds are post-horizon, this guard is inert and we tie again — but the new `deletion_request_audit` table gives the next Architect the exact tombstoned/spared decision per candidate, the missing half of the iteration-18 census. That is the cheapest honest probe the loop can run at this point.
## What changes
### 1. `store._honor_deletion_request` — deletion-scope guard (the behavioral change)
Current: the matcher tombstones every earlier record sharing ≥2 distinctive terms with the deletion request, where location proper-nouns ("River House", "Pine Harbor") and the `_CONTACT_SENSE_WORDS` vocabulary all count as distinctive terms. An appointment record "River House — pharmacy call Monday June 15 at 1:00 PM" shares {river, house} + {call/scheduling/appointment/front} with a "delete the River House line" request, crosses the ≥2 threshold, and its date/time is destroyed with it.
Rail the Developer must implement inside the matcher's decision, before `tombstone()` is invoked on a candidate `R` from request `Q`:
1. Compute `Q`'s deletion signature: does `Q` carry a phone digest (a `_PHONEISH_RE` match) or the synthetic contact tag?
2. Compute `shared_non_loc = (distinctive(Q) ∩ distinctive(R)) \ location_set`, where `location_set = Q`'s proper-noun place tokens + `_CONTACT_SENSE_WORDS` + the `_CONTACT_TAG`. "Place tokens" are the shared bigram/unigram tokens that name the facility (matched by a lightweight heuristics: tokens appearing in `Q` adjacent to `house|harbor|clinic|bridge|river|steps|...` — the Developer should reuse whatever term extraction `_honor_deletion_request` already performs, classifying each token as location vs content).
3. **Spare** `R` (do not tombstone, record `decision='spared_logistics_guard'` in the audit table) iff:
   - `Q` is a contact-line signature (step 1 true), **and**
   - `shared_non_loc` is empty (R's only overlap is facility + contact vocabulary — R is an appointment *at* the facility, not the line *of* the facility), **and**
   - `R` shares **no** phone digest with `Q` (the line record itself carries the number → it is the true target and is deleted as before).
4. Otherwise tombstone exactly as today.
Phone-digest and real-content overlap are hard overrides that keep the intended target deleted; only the location/contact-shadow appointment is spared. Existing deletion tests (`test_deletion_scope.py`) continue to pass: the `SECRET` request matches t001 by its phone digest; t002 (metformin) shares nothing.
### 2. `deletion_request_audit` table
New in-schema audit mirroring `access_log` for the tombstone path. One row per candidate the matcher decided on, with the flags that justify the decision. This is the observability the iteration-18 census lacks and the only way the next Architect can tell "over-match destroyed the gold" from "gold was post-horizon" for 013/020/021 without burning another tied iteration. Diagnostic-only; it never branches a decision (the insert happens after the decision is final), so it cannot move U/A/F by itself — it travels with the guard.
## What stays untouched
- `top_k`=16 hard cap: measured best, do not raise (iter-12 regression documented in both agent.py and the test suite).
- The logistics rescue and verbatim body append: present and wired on both LLM and no-LLM paths; they read only `allowed`/live rows and are not the failure.
- RBAC gate order (gate-0 responsiveness before policy gates): the property the whole label system rests on; this diff changes zero lines of `retrieve()` or `sanitize_and_decide`.
- 010's action-label failure (`answer_redacted` from 3 RBAC denials): policy-blind from where we stand; the census emitted in `debug.patient_census` will name those three record_ids after the run, but I spend no step guessing at a relationship upsert now. It is honestly budgeted as possibly-unfixed (+0 worst case −0.0556 if it was fixable and isn't).
## Storage constraint / SQL-only
No vector, graph, or document store is introduced. The only schema delta is one CREATE TABLE + one CREATE INDEX plus the `SCHEMA_VERSION` bump to 7. Both MUST requirements are preserved: the release surface is still `retrieve()` → (tombstone/RBAC/scope gates) → `sanitize_and_decide`, and active forgetting (body erasure to `''` for routine, key shredding for confidential) is unchanged — the guard only makes *fewer* records eligible for it, never recovers one that went through it.
