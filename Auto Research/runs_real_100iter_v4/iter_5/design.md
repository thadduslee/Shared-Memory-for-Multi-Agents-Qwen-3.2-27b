# Design — iteration 5 (standard_retrieval)
## Reading the table before designing
**What the measurements actually say.** U rose in the last two iterations (+0.0556, then +0.0261 MGS) — targeting U has not been a losing strategy here; iter 1→2 tied, 2→3 and 3→4 both gained. The meaningful regression in the newest row is not U but **A: 0.0000 → 0.0588**. MGS is multiplicative, so iteration 4's U gain was diluted: it bought +0.0556 of U and paid −0.0294 through (1−A). If I ship iteration 4's *type* of change again — widen what retrieval considers — without reining in the mechanism that let one privacy checkpoint leak, I get the same diluted outcome. So the plan has two coupled goals:
1. **Hold A where it is or better.** Every change below is an "which records are considered / how the label is derived" change, and releases only continue through the existing RBAC/scope/tombstone gates. No grant is widened. The A-regression vector from iteration 4 (the widened `top_k` default, which put more cleared-but-questionably-related rows in front of short answerers) must not be re-opened casually; the ranking fix in Mechanism 1 is the tool that lets the widened cap add *relevant* rows instead of chatty ones.
2. **Fix the nine checkpoints the census named**, because they are concrete selection/label errors that cost U with zero A/F content. They cluster three ways, and all three are fixed inside the retrieval loop at the "what is it about and does it matter" layer, not in the policy.
The iteration-4 critique is exactly the census: 7 checkpoints where `allowed == top_k == 11` saturated the cap (gold record ranked 12th or lower; ranking uses total-overlap, so chatty rows win on digit-run/contact vocabulary), 1 checkpoint where `answer_redacted` fired even though the allowed union was complete (per-record overlap, not marginal content, drives `query_answer_denials`), 1 checkpoint where a structural-only tombstone overlap silenced an answerable query. Those are three concrete, low-risk fixes, and they are what I ship.
---
## The three mechanisms and the changes
### M1 — Top-k truncation is a ranking bug, not a cap bug (7 checkpoints)
Every failing checkpoint shows `allowed = 11`, `denied_* = 0` — the cap did its job and the gold record was ranked 12th+. It is out-ranked because the sort key is `(total_overlap, structural, seq)`, and total overlap counts digit-runs and the synthetic `__contact__` tag. A sparse gold logistics/date record (`"Friday April 4 at 2:00 PM"`) shares digit-run and contact digests with chatty narrative rows that reuse the same vocabulary with *more* total overlap but no more **content** overlap.
**Change:** rank live candidates by *real-content* overlap first. The store already computes `content` (overlap restricted to non-structural digests) in PASS 1 and stores `structural = total - content` in the tuple; the sort key only needs to put `content` before `total` and `structural`. This is a one-line key change:
```python
candidates.sort(key=lambda item: (item[0] - item[1], item[0], item[1], item[2]), reverse=True)
```
where `item[0]` = total overlap, `item[1]` = structural count, `item[2]` = seq. This converts the candidate ordering so the sparse-logistics gold record (content 2–3) outranks a chatty row (content 1, but digit/contact overlap making total 4). The cap itself and the `top_k=8`/`top_k=1` test contracts are untouched because they call `retrieve(top_k=…)` directly with explicit values.
I also raise the **agent** default (`GateMemAgent.__init__`, `top_k: int = 11`) to `16` — with the M2 marginal-accounting fix in place, the extra evaluated-and-denied candidates this raise exposes no longer flip clean `answer`s to `answer_redacted`, which is the exact failure that made the prior 8→21 experiment collapse. The `retrieve` signature default stays `8` (pinned tests pass explicit values anyway).
**Local tests touched:** none (no test pins agent default; hard-cap and relevance-over-recency tests pass explicit `top_k`).
### M2 — `query_answer_denials` counts marginal, not per-record, content (1 checkpoint)
Checkpoint `…010…ckpt_09` got `answer_redacted` although the Judge confirmed the allowed union was complete. Gate 2/3 increment `query_answer_denials` when a denied record shares `≥ 2` real content words with the query — but ten records that all overlap the query are not ten withheld answers when their content is already in the allowed union. `sanitize_and_decide` behaves correctly; its input is wrong.
**Change:** inside `retrieve`, maintain a running set of *content* term hashes already seen in `allowed` (from the same `content_hashes` used for gating). For each gate-2/gate-3 denial, only increment `query_answer_denials` if the record's overlap with the query's `content_hashes` includes a digest **not yet in the allowed union**. Implementation sketch: as `allowed` fills, query the record's `record_terms` rows for content digests matching `content_hashes`, add them to a set; when a denial is processed, its matching content digests minus the allowed set determine whether it withholds anything new. A denial whose vocabulary is a subset of the allowed union withholds nothing answerable → `qad` stays 0 → branch 3 in `sanitize_and_decide` does not fire → label is `answer`.
This is the lever that makes the M1 `top_k` raise *safe*: all the extra near-miss candidates that get evaluated-and-denied under the wider cap will have content that is already represented in the wider allowed set.
**Local tests:** `test_that_denial_free_decision_produces_a_clean_answer` (action = `answer`) is preserved; hand-built `Decision`s in tests keep `query_answer_denials=None` and follow the back-compat path through `sanitize_and_decide`.
### M3 — Tombstone responsiveness excludes structural-only overlap (1 checkpoint)
Checkpoint `…017…ckpt_13` shows `allowed=11`, `denied_tombstone=4`, `action=no_memory` on a query the live records could answer. The fault: `tombstone_terms` preserves *all* digests, including digit-runs and `__contact__` (a phone-bearing or contact-word query shares the `__contact__` digest with every deleted logistics record in the shard), so a **structure-only** overlap wins gate 1 over eleven fully authorized records.
**Change:** make gate 1 use the same structural/content split gates 2/3 already use. `record_terms` and `tombstone_terms` each gain an `is_structural` flag, set at index time via `_is_structural_term`, propagated verbatim in `tombstone()`. `_is_responsive`'s tombstoned branch counts overlaps only over `is_structural = 0` rows; it falls back to `_DEFAULT_OVERLAP` only when the tombstone has **no real-content rows at all**.
This is the DDL change; it is explicit and named below. The F-tests (`test_deleted_content_is_not_retrievable_by_anyone`, `test_tombstone_beats_authorization`, `test_deletion_survives_reingestion…`) all query the deleted fact by its *own content words*, which retain real-content overlap and still trip `no_memory`. A query that reconstructs a deletion needs its content words, not digits and a contact tag.
**Local tests:** schema version bump and migration must be non-breaking on the fresh per-episode file (each episode opens an empty store).
**Schema/DDL for M3** (baseline update in `schema.sql` plus the migration):
```sql
-- Migration 5 (SCHEMA_VERSION 4 -> 5)
ALTER TABLE record_terms
    ADD COLUMN is_structural INTEGER NOT NULL DEFAULT 0;
ALTER TABLE tombstone_terms
    ADD COLUMN is_structural INTEGER NOT NULL DEFAULT 0;
CREATE INDEX IF NOT EXISTS idx_tombstone_terms_structural
    ON tombstone_terms(record_id, is_structural, term_hash);
-- rationale: gate-1 tombstone scan filters preserved digests by is_structural=0,
-- so the index must be keyed by (record_id, is_structural, term_hash).
```
---
## Safety posture (A and F)
This design keeps the **three gates in order** and extends the structural/content split to gate 1 rather than deleting any gate. No grant is widened; the only releases that change are rows that already passed RBAC/scope, and they are more *relevant* rows rather than a broader mixture. F-probes are unaffected because real-content digests still trip `no_memory`; the only tombstone rows that become non-responsive are those whose sole overlap is digits/contact, which cannot reconstruct a deletion.
**MGS impact.** The census names nine checkpoints whose expected content/label is present but missed or mislabeled. On a dev slice where U=0.5 from ~18 utility checkpoints, fixing all nine moves U toward the 0.85 target region if the fixes generalize (U ≈ 45/50 of dev checkpoints overall is not the right denominator — the slice is mixed utility/privacy/probes — but the directional gain is the largest remaining lever). Holding A at or near 0 and F at 0 is what keeps the multiplier from eating the gain.

- `memory_system/agent.py` — agent default `top_k = 16` (comment updated).
