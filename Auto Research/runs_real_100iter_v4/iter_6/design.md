## Iteration 6 design — stop moving retrieval; fix the answer boundary and the tombstone override threshold
The census is unambiguous. Both named mechanisms are *decision-layer* faults — not candidate-scan faults — and neither needs new DDL. Mechanism 1 exonerates retrieval outright (four of six checkpoints never hit the `top_k=16` cap; 12–16 cleared records with verbatim logistics gold were already in `allowed`, and the answerer simply summarized 2–9 of them into prose that dropped the strings). Mechanism 2 exonerates M5's `is_structural` split (correct and already applied) and indicts the *admit threshold* in `retrieve()`'s gate 1: any overlap (`total > 0`) lets a tombstone flip 16 live, complete answers to `no_memory`.
The last three iterations chasing U inside `retrieve()`'s scan/top_k/sort stalled; this one does not touch that machinery at all.
Targets: `U` in the clearest — M1 (≈6 checkpoints) and M2 (1 checkpoint ckpt_13). The one place I must not break is `test_a_tombstoned_record_is_assumed_responsive`, which forces `no_memory` when a query has **zero** overlap with a tombstone (conservative when nothing else responsive exists). That is compatible with the desired M2 fix as long as I distinguish "weak single-word overlap but abundant live evidence" from "no live evidence at all".
Mechanism 1 fix (in-package, deterministic, no gold leakage): after rendering (including via the injected LLM), scan the already-cleared `allowed` bodies for logistics tokens (dates, times, phone patterns, dose units), and verify each occurs verbatim in the final answer string. Any missing token is appended as an explicit `"Required logistics details:"` list. Because it only re-emits content that already cleared the gates, it cannot raise A; because it is token-level, it survives summarization. The deterministic no-LLM path already joins bodies, so this backstop is a no-op there, keeping it cheap.

## Mechanism 1 — `answered_but_content_missing` (6 checkpoints, dominant term)
The candidate scan is exonerated. The critique honestly flags a risk: the prompt text lives in the injected LLM wrapper outside this package, so instruction edits may be harness-capped. ## Mechanism 2 — `evidence_withheld` (1 checkpoint, tombstone threshold)
`med_episode_rewrite_en_017...ckpt_13` fires `no_memory` (allowed=16 live, denied_tombstone=4) because gate 1 admits a tombstone on **any** overlap (`total > 0`). One incidental shared content word across several deleted records silences an otherwise-complete live answer. The codebase already uses `>= 2` real-content digests as the answer-bearing bar in gates 2/3 and in `_honor_deletion_request`; gate 1 should apply the same bar — **but only when independent live evidence exists**. A query with *no* live responsive candidates must stay conservative (tombstone assumed responsive) — that is exactly what `test_a_tombstoned_record_is_assumed_responsive` locks in, and it is the correct call when there is no other evidence.
New gate-1 rule:
- If the episode has **any** live responsive candidate (one that clears gate 0 and is not itself tombstoned) that would substantiate an answer, a tombstone only fires when it shares `>= 2` real-content (`is_structural=0`) digests.
- If there is **no** live responsive candidate at all, a tombstone fires even on zero/weak overlap (conservative `no_memory`), preserving the unit test and the F-contract tests that only target tombstoned records with no live residue.
This keeps every F test green because:
- `test_deleted_content_is_not_retrievable...` — tombstoned secret vs "callback number": two so the 2+ bar fires, but even in the no-live branch it would.
- `test_tombstone_beats_authorization` — same, fires.
- `test_a_tombstoned_record_is_assumed_responsive` — no live responsive records, fires.
- The one ckpt_13 — live allowed=16 exists, shared overlap is < 2, so no tombstone fire → `answer` restored.
No new DDL; M5's `is_structural` schema is correct. Migration SQL is empty (zero new statements).
