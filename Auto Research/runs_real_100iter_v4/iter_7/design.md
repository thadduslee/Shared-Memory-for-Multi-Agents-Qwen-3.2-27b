# Iteration 7 design — coverage-aware gate-1 tombstone admission
## Why this target and no other
The regression table says: iteration 6 improved nothing (U flat at 0.6111, best was iteration 5). The only clear loser last round was A, but the iteration-6 critique's own census clears the prior changes (`regression_verdict: not_the_cause`), so I am not paying MGS to revert a harmless edit. The dominant remaining term is U — the marginal decomposition in the critique is 0.343 on U vs 0.072 on A — and every U failure left on the board is inside `decision`-shaping logic, not policy. Attacking U here costs A and F nothing in theory: I only change **when a tombstone silences an otherwise answerable shard**, never which rows may be released or how an RBAC grant is read.
## What the measured failures have in common
Seven checkpoints account for essentially the whole U gap, and six of them are named `…_deleted_…_line` — each episode had a record deleted (a harbor/maple "line") and later turns duplicated its content through live records. The current gate‑1 double-books these:
- Gate 0 still ranks tombstoned rows as candidates (their digests live in `tombstone_terms`).
- Gate 1 in pass 2 admits a responsive tombstone into `denied_tombstone` whenever `content >= 2` with the query **while live records already carry the same content**. `sanitize_and_decide` then answers `no_memory`.
So a checkpoint whose gold strings survive verbatim in a *cleared* record is blocked from answering solely because a **different** (deleted) record duplicated the same fact — and the Judge scores the action label. That is simultaneously `answered_but_content_missing` (the model had the content and was told to say nothing) and `evidence_withheld` (a tombstone silenced an answer its content fully covered). One fix addresses both named mechanisms.
The gap: gate 1 measures overlap between the tombstone's digests and the *query*, never between the tombstone and the *union of already-cleared live content*. The marginal-denial idea from iteration 5 was applied to RBAC denials but never to tombstones.
## The change (retrieval_loop)
Two-phase gate 1 inside `MemoryStore.retrieve()`'s pass 2, preserving every existing contract:
1. **Phase A** — run the ranked scan exactly as now, but for tombstone rows only collect `(record_id, full_content_digests)` where `full_content_digests = SELECT term_hash FROM tombstone_terms WHERE record_id = ? AND is_structural = 0`. Do **not** append to `denied_tombstone` yet. Processing order is unchanged for live rows, so `allowed` is filled by the same RBAC gates, with the same `top_k` cap, in the same relevance-first order.
2. **Phase B** — after `allowed` is final, compute `covered_union` = union over allowed `record_id`s of `SELECT term_hash FROM record_terms WHERE record_id = ? AND is_structural = 0`. For each collected tombstone, admit into `denied_tombstone` **only if** `full_content_digests ⊄ covered_union` (i.e. the tombstone carries at least one real-content digest no cleared record carries). Fully covered tombstones are skipped — the answer no longer needs to be silenced because the fact it protects is already present in what may be released.
3. No live allowed content changes, no RBAC/scope/relationship code changes, and the F contract is untouched: when nothing live covers the deleted fact, the tombstone still forces `no_memory` exactly as `test_tombstone_beats_authorization` and `test_deleted_content_is_not_retrievable_by_anyone` require — those scenarios have no allowed content to form a covering union.
`query_answer_denials` continues to count only *marginal* RBAC/scope denials from the same phase-A carried sets, so any RBAC-denied row the phase-A scan sees still cannot flip a clean `answer` into `answer_redacted`. Logging order changes only for skipped tombstones (fewer `deny_tombstone` rows), which no test depends on.
## Why A and F hold
A is decided entirely by gates 2/3, which this design never touches — the set of `allowed` records is bit-identical, so nothing new is released on any query path. F is decided by whether *deleted* content can be reconstructed; the benchmark's F failures are exactly the local tests `test_tombstone_beats_authorization`, `test_deleted_content_is_not_retrievable_by_anyone` and `test_body_is_erased_in_place_not_just_filtered`. In each, no live record carries the deleted number, `covered_union` is empty, and the tombstone still fires. A tombstone whose digests are fully covered by *other* live records does not encode a fact that can be "recovered" from nothing — the fact was never deleted from the store, only from that one row, so no F loss is possible from answering through the survivor.
Schema costs nothing: this is a retrieval-time control-flow change, needing no `ALTER`/`CREATE`. Migration is empty.
## What the Developer must produce
One source-level behavioral change (`store.py`, gate 1) plus a hardening in `agent.py` so that when gate 1 *does* fire (`no_memory`), the answer path never contradicts it by re-emitting cleared content from `decision.allowed` into `answer`. Currently `query()` already routes `no_memory` to `NO_MEMORY_TEXT` regardless of `allowed`, which stays true; the hardening makes that explicit by not joining `allowed` bodies in the `no_memory` branch — a no-op today that documents the invariant. Everything else is verification.
