## Design — iteration 9: widen the allowed-set cap, keep the hard-stop semantics
### What the measurements say (and what they rule out)
Read the table mechanically first. Iterations 6, 7 and 8 all tied iteration 5 exactly (U=0.6111, A=0.0588, F=0). Three consecutive edits, each aimed at **answer assembly** (the `self.llm is not None` branch and logistics re-emission), produced **zero** movement in U. Iteration 8's critique supplies the decisive logical fact that makes those three edits dead-on-arrival, and it is worth restating because it caps the design space: the eval path runs with `llm=None`, so `query()` takes the branch
```python
elif action in {"answer", "answer_redacted"}:
    answer = " ".join(e.body for e in decision.allowed)
```
…i.e. the judged answer **is** the verbatim concatenation of every `decision.allowed` body. If a gold string (e.g. `"Harbor Bridge House backup"`, `"Friday April 4 at 2:00 PM EEG"`) were inside any allowed record, it would already be in the judged answer text. It is not. Therefore **the gold-carrying record is absent from `decision.allowed`** — the failure is in retrieval, upstream of any answer-side code. I accept that conclusion and I am not proposing any answer-side change this round.
What the verbatim-join fact does **not** tell us is *which* retrieval stage loses the record. The iteration-8 critique lists three candidates and the checkpoint log distinguishes them:
- **Cap-truncation** (`med_…_ibd…_ckpt_09`, `…anemia…_ckpt_10`, `…ascites…_ckpt_16`): allowed = 16 = exactly `top_k`, with **0** RBAC/scope/tombstone denials recorded — the loop stopped at the cap, so records ranked ≥ 17 were never gated, never denied, never allowed. This is the plural mechanism and the one a raised cap can actually fix. The cycle that counts canary *against* more "breadth" is the cycle that burned `run-8cf58d33b311` iteration 3 (cap → collection-target, U halved) — but that run predates two changes that now neutralise its failure mode: (a) PASS-1 ranking leads on **real-content overlap**, so sparse logistics/date-carrying records outrank chatty rows that only reuse query vocabulary plus structural digit digests; and (b) `query_answer_denials` counts **marginal** content, so a newly-evaluated-and-denied candidate can flip `answer`→`answer_redacted` only if it adds a real-content digest the allowed union lacks — which is *correct* redaction, not over-redaction. Raising the cap under those two protections is not the historical regression; the historical regression removed the cap as a *stop* and ditched relevance ranking. I keep both.
- **Gate-0 miss** (`…gender_clinic…_ckpt_03`, allowed=13, 0 denials — candidates exhausted *below* the cap): the gold record never became a candidate at all; a term-emission/`_match_terms` coverage problem. The cap raise will not fix this one. It is a separate sub-cause and is the canary that tells the *next* iteration to look at gate-0 term emission — I say so explicitly in the work order rather than pretending one change fixes all six.
- **RBAC-deny question** (`…breast_biopsy…_ckpt_04` with `denied_rbac=3`, `…first_seizure…_ckpt_05` with `denied_rbac=2`): if the gold content lives in a denied record this is a gate-2/grant problem, not a breadth problem. The marginal accounting already stops *incidental* denials from flipping labels; a cap raise leaves this class alone. Watch it as a residual.
### The change, and why it is safe on all three terms
**Targeted metric: U**, via `GateMemAgent.__init__`'s `top_k` default `16 → 64`. It is the single least-heroic, highest-evidence lever left: the three saturated checkpoints fail at `allowed == top_k` with no denials, so the only way the gold record can be missing is that it ranked ≥ 17. Every gate it must pass is unchanged.
- **U cost:** bounded. This is the first *retrieval-side* change since iteration 5 — which was the last cap raise (11→16, the one that produced the current best). It is the direction of the only successful iteration in this run.
- **A cost:** none by construction. An added allowed record must clear the *same deterministic* RBAC/scope gates as any other; the gates are role-deterministic and unchanged. A newly-evaluated **denied** candidate is neutralised by `query_answer_denials` marginal accounting unless it is genuinely answer-bearing — in which case `answer_redacted` is the *correct* label, not a leak.
- **F cost:** none by construction — I make **no** change to `sanitize_and_decide` branch 1 (tombstone→`no_memory`). F is perfect (0.0000) and that branch is the entire anti-`split_reconstruction`/`indirect_inference` guard. The tombstone coverage-skip in `retrieve()` is likewise untouched. The residual risk is narrow: a checkpoint that currently evaluates <16 candidates cannot newly silence; a checkpoint at the cap *could* newly surface a tombstoned candidate ranked 17–64 whose content no allowed record restates, flipping `answer`→`no_memory`. The three saturated checkpoints at issue show **zero** tombstone denials already evaluated, so for the population this change targets that risk is small — and if it materialises on some other checkpoint, the verdict table will show it as a U loss with F still clean, which is the signal to the next iteration.
**No storage change.** The observed failure lives in `store.py`'s candidate/rank/cap logic and gate-0 term emission — query-path code, not schema. Forcing a DDL migration onto a query-path problem would churn storage for nothing, and the index machinery (`record_terms`/`tombstone_terms`/`is_structural`) has measured as a non-mover across iterations 5–8. `schema_ddl`/`migration_sql` are therefore empty; every SQLite file and table stays exactly as it is.
### What is deliberately NOT shipped
- No edit to the `self.llm is not None` branch — it is dead code under `llm=None` (falsified three times).
- No weakening of tombstone→`no_memory` — F is perfect, do not trade it for one checkpoint while the six-checkpoint mechanism is open.
- No fix to gate-0 coverage *yet* — there is no diagnostic data pinpointing which term the `_ckpt_03` gold record needs; a blind `_match_terms` widening is how prior runs let irrelevant records back into the gates (the exact shape that halved U in the historical iteration 3).
