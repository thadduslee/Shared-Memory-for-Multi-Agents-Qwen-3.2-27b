# Iteration 1 — Design Document
## Read on the measurements
U = 0.000, A = 1.000, F = 1.000 is the signature of a **never-run / structurally-broken retrieval path**, not of a tuned system that failed at the margin. The existing local suite (`test_rbac.py`, `test_forgetting.py`, `test_deletion_scope.py`) already encodes the correct A/F behaviour for the contract scenarios: confidential-at-rest, tombstone-before-RBAC, `no_memory` for tombstone hits even to authorized askers, key-shred + in-place body erase, idempotent `tombstone()`, scope-limited family grants. So the policy layer for A and F is largely *present*; what the measurements say is that **U is the collapsed term** (0.000), which drags MGS = U·(1−A)·(1−F) to zero regardless of A/F.
The single biggest cause of a structural U=0 in the baseline is the **hard relevance gate** in `MemoryStore.retrieve`:
```python
if terms and not (terms & _distinctive_terms(plaintext)):
    continue  # simply not relevant; not a policy denial
```
A utility query phrased generically — e.g. *"what should I take"* against a stored `"Stop ibuprofen; start acetaminophen 650 mg."` — shares **zero** content tokens with the record (`take` is not in the stopword list, but the record body contains neither `take` nor `what`). The row is dropped, `decision.allowed` is empty, `sanitize_and_decide` returns `no_memory`, and U scores zero on every paraphrase-style checkpoint. That is the term this iteration attacks.
Secondary U-killer: `_honor_deletion_request` **requires ≥2 overlapping tokens** between the delete request and a prior record. A request like *"forget the number I gave you"* shares at most one token with the stored record and is silently ignored — which is also an F leak (the deleted fact stays retrievable) and a U/L contradiction. Fixing matching protects F **and** keeps U alive.
## What this iteration targets
- **Targets: U (utility).** Fix the two structural zeros above so `retrieve` actually returns evidence on paraphrase/natural-language queries, while keeping the RBAC/tombstone gates untouched.
- **A and F are held, not traded.** Every change below operates *after* the three gates (tombstone → role-grant → relationship+scope). No change widens the visibility set; it only changes which *already-cleared* records get surfaced. The existing local suite stays green and is the regression guard.
- **Cost:** a modest, bounded over-inclusion risk — a relaxed relevance floor can surface more cleared records, which can flip `answer`→`answer_redacted`/`refuse` in edge cases (because `touched_unauthorized` sees more candidates). That costs a little U, never A or F. The floor is ordered by score so it is the *highest-*scoring candidates, not everything.
## Schema changes (SQL only, one file per run)
No new tables. Two indexes accelerate the query paths this iteration touches:
1. `idx_records_episode_author_seq` — accelerates the deletion-fallback scan in `_honor_deletion_request` (`WHERE episode_id=? AND author_id=? ORDER BY seq DESC`).
2. `idx_accesslog_checkpoint_requester` — accelerates the audit-path and Critic evidence query `WHERE checkpoint_id=? AND requester_id=?`.
Emitted as `CREATE INDEX IF NOT EXISTS` in `migration_sql` (idempotent, safe on an existing store). The full baseline DDL is emitted in `schema_ddl` unchanged.
## Retrieval loop (store.py)
Keep the gate order **tombstone → role-grant → relationship+scope → decrypt** exactly as-is; it is what makes A and F correct. Replace the hard relevance drop with a **scored relevance pass with a floor**:
- During the scan, records that pass all three gates but score 0 on relevance are *retained in a `pending` bucket* instead of `continue`-dropped.
- After the main scan, if `decision.allowed` is empty (and `top_k` not yet reached), promote the highest-scored `pending` candidates (ordered `score DESC, seq DESC`) up to `top_k`.
- Scores come from a new helper `_relevance_score(query_terms, record_terms)` that rewards shared tokens **and** shared character bigrams (catches morphology and paraphrase: `dose` vs `dosage`, `take` vs `taking`), with token hits weighted higher.
This guarantees `retrieve` returns *something cleared* on natural-language queries without ever bypassing the gates. Also fixed: `_honor_deletion_request` gains (a) exact `record_id` matching when the request text contains the id, (b) normalized-phrase matching (digit+whitespace-collapsed) when the token overlap < 2, and (c) a final fallback that tombstones the most recent non-deleted record by the requester in the episode when nothing matched — so a delete is **never silently ignored** (protects F and keeps U honest).
## Active forgetting (unchanged core, hardened edges)
The mechanism — tombstone row + in-place `body=''` erase for plaintext, cryptographic key-shred (`crypto_keys.key_material=NULL`, `records.key_id=NULL`, `shredded_at` audit stamp) for confidential records, and `Decision.denied_tombstone` forcing `no_memory` even for authorized askers — is correct and test-locked. This iteration only hardens the *matching* that feeds it (delete-request matching above) and expands `_DELETE_REQUEST`/`_CONFIDENTIAL_MARKERS` modestly (`sensitive`, `suicid`, `overdose`, `hospice`, `don't store`, `remove`).
